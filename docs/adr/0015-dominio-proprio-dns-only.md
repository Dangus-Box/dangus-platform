# Cada Produto usa domínio próprio na sua zona, em DNS-only

Cada Produto declara seus domínios na Config do Produto, em vez de depender da zona da Plataforma. O Registro consulta `GET /zones?name=` pelo maior sufixo existente na conta Cloudflare, incluindo `.com.br`, e aceita o apex ou um nível de subdomínio. `platform__CLOUDFLARE_ZONE_ID` deixa de ser necessário; o token DNS precisa de Zone:DNS:Edit e Zone:Zone:Read em “All zones from an account”. Instalações existentes exigem rotação humana de `platform__CLOUDFLARE_DNS_TOKEN` no BWS. Zona ausente gera orientação; CNAME, proxy ligado, IP divergente ou duplicatas interrompem o Registro sem sobrescrever DNS.

Os registros A e AAAA ficam em DNS-only e apontam para o Host, usando os endereços de `analytics.dangus-box.com`. O TLS termina no kamal-proxy, com certificados Let's Encrypt via HTTP-01 e portas 80/443 públicas. O proxy da Cloudflare fica para quando houver origem restrita: hoje seria possível contorná-lo acessando o Host diretamente, portanto `CF-Connecting-IP` é um header fornecido pelo cliente e não é confiável.

## IP do cliente e evidência

Com `ssl: true` e sem habilitar `forward_headers`, o kamal-proxy v0.9.2 **sobrescreve** `X-Forwarded-For` com o IP do par da conexão; não acrescenta o valor recebido do cliente. A App pode usar esse header apenas quando a entrada passa exclusivamente pelo kamal-proxy e essa configuração é preservada. NAT pode fazer o IP observado representar o gateway; não se deve presumir que ele identifica uma pessoa.

Verificado em 17/11/2026 no Host `devbox-1`: `kamal-proxy list` mostrou v0.9.2 com TLS ativo para `api-sqlite.dangus-box.com` do Produto `exemplo-sqlite`. A requisição `curl -H 'X-Forwarded-For: 198.51.100.82' 'https://api-sqlite.dangus-box.com/ready?xff-probe=issue82-verification'` retornou `{"status":"ok"}`; uma captura temporária no namespace de rede do container da API imprimiu exclusivamente o header recebido: `X-Forwarded-For: 172.16.5.1`. O IP forjado desapareceu; o endereço privado é o par visto neste acesso local com NAT. A captura foi removida, sem alterar a App ou o proxy, e nenhum DNS real foi gravado.

O [deploy da versão v0.9.2](https://github.com/basecamp/kamal-proxy/blob/v0.9.2/internal/cmd/deploy.go#L99-L101) define `ForwardHeaders = !TLSEnabled` por padrão. O [encaminhamento](https://github.com/basecamp/kamal-proxy/blob/v0.9.2/internal/server/target.go#L344-L359) só preserva o XFF recebido quando `ForwardHeaders` está ativo; o [teste oficial](https://github.com/basecamp/kamal-proxy/blob/v0.9.2/internal/server/target_test.go#L181-L264) cobre ambos os modos. Com `forward_headers: true`, passa a **acrescentar** o IP ao header recebido; a orientação acima deixa de valer. Sem TLS, o padrão também é encaminhar os headers recebidos.
