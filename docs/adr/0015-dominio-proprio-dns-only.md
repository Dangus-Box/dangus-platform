# Cada Produto usa domínio próprio na sua zona, em DNS-only

Cada Produto declara seus domínios na Config do Produto, em vez de depender da zona da Plataforma. O Registro consulta `GET /zones?name=` pelo maior sufixo existente na conta Cloudflare, incluindo `.com.br`, e aceita o apex ou um nível de subdomínio. `platform__CLOUDFLARE_ZONE_ID` deixa de ser necessário; o token DNS precisa de Zone:DNS:Edit e Zone:Zone:Read em “All zones from an account”. Instalações existentes exigem rotação humana de `platform__CLOUDFLARE_DNS_TOKEN` no BWS. Esse token alcança todas as zonas da conta, inclusive `dangus-box.com`; o vazamento dele tem esse alcance. Zona ausente ou ainda não ativa (por exemplo, `pending`) gera orientação sem gravar DNS, sem recorrer à zona pai; CNAME, proxy ligado, IP divergente ou duplicatas interrompem o Registro sem sobrescrever DNS.

Os registros A e AAAA ficam em DNS-only e apontam para o Host, usando os endereços de `analytics.dangus-box.com`. O TLS termina no kamal-proxy, com certificados Let's Encrypt via HTTP-01 e portas 80/443 públicas. O proxy da Cloudflare fica para quando houver origem restrita: hoje seria possível contorná-lo acessando o Host diretamente, portanto `CF-Connecting-IP` é um header fornecido pelo cliente e não é confiável.

## IP do cliente e evidência

Com `ssl: true` e sem habilitar `forward_headers`, o kamal-proxy v0.9.2 **sobrescreve** `X-Forwarded-For` com o IP do par da conexão que ele recebe; descarta o valor enviado pelo cliente. A App pode usar esse header apenas quando a entrada passa exclusivamente pelo kamal-proxy e essa configuração é preservada. O que está provado é que o cliente não consegue forjar o header; **não** está provado que o par visto pelo kamal-proxy é o IP público de um cliente externo. A publicação de portas do Docker (NAT, `userland-proxy`, IPv6 pelos registros AAAA) pode trocá-lo por um endereço de gateway. Até uma verificação a partir de um cliente fora do Host, trate o valor como “par do kamal-proxy”, não como IP do cliente, e não presuma que ele identifica uma pessoa.

Verificado em 17/11/2026 **a partir do próprio Host** `devbox-1`, não de um cliente externo: `kamal-proxy list` mostrou v0.9.2 com TLS ativo para `api-sqlite.dangus-box.com` do Produto `exemplo-sqlite`. A requisição `curl -H 'X-Forwarded-For: 198.51.100.82' 'https://api-sqlite.dangus-box.com/ready?xff-probe=issue82-verification'`, executada no Host, retornou `{"status":"ok"}`; uma captura temporária no namespace de rede do container da API imprimiu exclusivamente o header recebido: `X-Forwarded-For: 172.16.5.1`. O IP forjado desapareceu; `172.16.5.1` é o endereço privado com que essa conexão local chegou ao kamal-proxy, após NAT. Isso basta para a semântica (sobrescrever ou acrescentar não depende da origem da conexão, só de `ForwardHeaders`), mas não para o IP de clientes externos. A captura foi removida, sem alterar a App ou o proxy, e nenhum DNS real foi gravado.

O [deploy da versão v0.9.2](https://github.com/basecamp/kamal-proxy/blob/v0.9.2/internal/cmd/deploy.go#L99-L101) define `ForwardHeaders = !TLSEnabled` por padrão. O [encaminhamento](https://github.com/basecamp/kamal-proxy/blob/v0.9.2/internal/server/target.go#L344-L359) só copia o XFF recebido quando `ForwardHeaders` está ativo; em seguida chama [`SetXForwarded`](https://pkg.go.dev/net/http/httputil#ProxyRequest.SetXForwarded), e o [`ReverseProxy` do Go](https://github.com/golang/go/blob/go1.25.5/src/net/http/httputil/reverseproxy.go#L430-L437) com `Rewrite` remove `X-Forwarded-*` da requisição de saída antes disso, então sem a cópia resta só o IP do par. O [teste oficial](https://github.com/basecamp/kamal-proxy/blob/v0.9.2/internal/server/target_test.go#L181-L264) cobre ambos os modos. Com `forward_headers: true`, passa a **acrescentar** o IP ao header recebido; a orientação acima deixa de valer. Sem TLS, o padrão também é encaminhar os headers recebidos.
